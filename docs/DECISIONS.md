# 项目决策记录

最后核对：2026-09-16。本文件使用轻量 ADR 方式记录会影响后续开发的决定，防止新对话在缺少背景时反复推翻边界。

状态：`Accepted` 已采用；`Deferred` 明确延期；`Open` 尚需所有者选择；`Superseded` 已被后续决策替代。

## D-001 单仓库模块化单体

- 状态：Accepted
- 决定：Next.js 和 FastAPI 放在同一 `zhixian` 仓库，通过清晰目录和服务层保持模块边界。
- 原因：个人/小规模维护、共享发布节奏和单台阿里云部署不需要微服务复杂度。
- 后果：新增功能优先扩展现有模块；只有存在独立扩缩容、故障隔离或团队边界证据时才重新评估拆分。

## D-002 本地 SQLite，生产 PostgreSQL

- 状态：Accepted
- 决定：源码开发默认 SQLite，Docker/生产使用 PostgreSQL 17，SQLAlchemy + Alembic 维护一致模型。
- 原因：降低本地门槛，同时保留生产可靠性。
- 后果：模型和迁移必须双数据库验证；涉及约束、SQL 或并发的变更不能只测 SQLite。

## D-003 GitHub 是唯一代码同步中心

- 状态：Accepted
- 决定：主仓库为 `zhanghuiwan/zhixian`，`main` 保持可构建、可测试、可部署；阿里云只拉取仓库版本。
- 原因：保证跨机器、跨模型和服务器上的代码可追溯。
- 后果：不以网盘/复制目录同步代码，不在服务器直接修改源码；运行数据和密钥独立管理。

## D-004 单机 Docker Compose 部署

- 状态：Accepted（当前规模）
- 决定：Nginx、Web、API、PostgreSQL 通过 Compose 部署在单台阿里云 Ubuntu 主机。
- 原因：成本和运维复杂度适合个人/小规模产品。
- 后果：需要可靠备份、异地副本和恢复演练；规模、可用性或耗时任务增长后再评估对象存储、worker 和托管数据库。

## D-005 用户自带 AI Key，服务端加密

- 状态：Accepted
- 决定：用户配置 DeepSeek/MiniMax Key；后端用独立主密钥加密，Provider 地址白名单化。
- 原因：用户控制额度，知闲不集中持有统一厂商额度，同时避免浏览器持久保存完整 Key。
- 后果：主密钥必须与数据库配套恢复；读取接口只返回掩码；新增 Provider 需适配统一契约和安全测试。

## D-006 有界单 Agent + 领域工具

- 状态：Accepted
- 决定：模型只负责理解、选择工具和生成表达；数据库事实和写操作由注册工具执行。当前不使用子 Agent。
- 原因：权限、事务、确认、审计和成本更容易控制。
- 后果：不提供任意 SQL/HTTP/文件/代码执行；破坏性工具确认；出现明确独立角色和收益证据后才评估多 Agent。

## D-007 学习事实与模型记忆分离

- 状态：Accepted
- 决定：进度、历史、计划、生词和文章来自数据库实时查询；会话摘要和明确偏好只提供上下文。
- 原因：模型记忆不能作为可审计事实源。
- 后果：事实回答应调用工具；长期偏好只有白名单键且需用户明确授权。

## D-008 qwerty-learner 只作候选词库来源

- 状态：Accepted
- 决定：上游仓库不成为知闲子项目或运行依赖；通过固定提交、manifest、转换、校验和事务导入。
- 原因：隔离上游变化，保证复现、质量和用户数据安全。
- 后果：每个数据集单独做来源/授权审核；未经批准不能复制或生产导入。当前六个数据集由项目所有者批准纳入 Git，并随包保留上游许可副本和第三方提示。详细规范见 `WORDLIST_PIPELINE.md`。

## D-011 单一英文核心词书与数据库正式存储

- 状态：Superseded by D-012
- 日期：2026-09-07
- 背景：用户明确要求产品只保留一份英文词库，并选择四六级、考研、英语一/英语二和雅思词汇合并去重。
- 决定：产品只发布 `zhixian-core-en-v1`；正式单词、顺序、来源和用户进度进入关系数据库。规范化 JSONL 数据包和 manifest 一起留在 Git，作为新主机和新数据库的可重建基线。
- 原因：数据库能提供唯一约束、事务、查询、用户进度关联和 PostgreSQL 持久化；单个大 JSON 无法可靠处理并发、更新和审计。
- 后果：`0004` 增加词书稳定 slug 和来源表；六个源文件 21,739 条合并为 7,416 个唯一词条。Docker 启动和本地命令都从 Git 数据包幂等导入，不依赖上游目录。

## D-012 统一词典与独立系统预设词书

- 状态：Accepted
- 日期：2026-09-09
- 背景：用户指出把四六级、考研和雅思融合成一本产品词书不可取，同时允许底层词典统一去重。
- 决定：继续用 7,416 条合并数据维护全局 `words` 与来源审计；产品只发布四级、六级、考研通用、考研英语一、考研英语二和雅思六本来源预设。合并词书记录保留在数据库但取消发布，原来选择它的账号迁移到四级词汇。
- 原因：词典唯一可以让掌握进度跨词书共享，独立词书则保留考试目标、顺序和用户心智。
- 后果：manifest 显式声明 `publish_source_books=true`、`publish_merged_book=false`；导入仍然幂等。个人词书继续复用 `vocabulary_collections`，系统与个人入口以 `kind + id` 区分。

## D-013 每日默认会话与确定性上下文操作

- 状态：Accepted
- 日期：2026-09-15
- 背景：AI 是产品主页，但每次进入都新建会话会割裂上下文；纯英文输入和回答后的常用学习动作也不应依赖模型临时措辞。
- 决定：未指定会话时按用户本地日期复用唯一 `daily` 会话，显式“新对话”创建 `manual` 会话。英文单词、句子、长文由服务端确定性分类并注入本轮约束；最终操作按钮根据输入与已验证工具结果生成、持久化，前端仅执行白名单类型和站内路径。
- 原因：保持一天内自然连续的陪伴感，同时让自动翻译和学习动作稳定、可测试、可恢复，不从 Markdown 正文推断命令。
- 后果：迁移 `0007` 增加会话类型和本地日期；SSE `message.completed` 与消息读取契约增加 `actions`；详细查词/翻译正文与学习数据分离，加入词本只写词条关联或受限核心字段，收藏句子只写规范译文；新增动作需同步 schema、服务端生成规则、前端校验、权限测试和文档。

## D-014 分轮学习与整组提交

- 状态：Accepted
- 日期：2026-09-15
- 背景：单次按钮评分不能表达同一个词在一组内多次遗忘后才记住，逐次等待网络也会打断学习。
- 决定：学习页使用三个固定熟悉度和 0–100 滑杆，低于 80 分的词进入下一轮；未完成组按用户保存在浏览器，全部通过后一次提交完整答题轨迹。
- 原因：分数序列、错误次数和轮次比最终一次评分更能描述记忆稳定性；本地先行让网络波动不阻断当前学习组。
- 后果：迁移 `0008` 增加 `study_sessions` 和逐词轨迹字段；服务端以用户和客户端会话 ID 幂等提交，并在单一事务中更新进度。当前未完成组不能跨设备继续，后续复习算法直接消费组内轨迹。

## 新决策格式

```markdown
## D-NNN 标题

- 状态：Accepted | Deferred | Open | Superseded
- 日期：YYYY-MM-DD
- 背景：为什么需要决定
- 决定：选择了什么
- 原因：关键证据和取舍
- 后果：实施、迁移、安全、运维和文档影响
- 替代项：评估过但未采用的方案（如重要）
```

修改 Accepted 决策时新增一条决策并把旧项标为 Superseded，不要直接抹去历史理由。
