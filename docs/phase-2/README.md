## 1. 阶段目标

第二阶段将知闲从“固定页面驱动的英语学习工具”升级为“可对话、可查询、可执行的英语学习 Agent”。Agent 必须能够：

- 使用用户在设置中配置的 DeepSeek、MiniMax 等模型；
- 保存并恢复对话历史；
- 查询今天、昨天、前天及指定日期的真实学习记录；
- 查询今天和明天的复习计划，并区分确定计划与预测计划；
- 查词、生成例句、生成文章；
- 按需检索当前用户全部持久化会话中的关键词；
- 词库缺词时先征得用户同意，再创建仅该用户可见的自定义词；
- 新建、修改、删除自定义生词本，以及向指定生词本添加或移除单词；
- 根据明确的用户意图跳转到学习、文章、生词本等站内页面；
- 对删除、批量修改等高风险操作请求用户确认；
- 在桌面端和移动端保持完整可用。

核心原则：模型负责理解和规划，领域服务负责执行，PostgreSQL 是学习事实的唯一来源。

## 2. 系统边界

```text
浏览器
  └── AI 对话界面
        └── FastAPI Agent 编排器
              ├── Provider 适配层
              │     ├── DeepSeek
              │     ├── MiniMax
              │     └── 后续兼容厂商
              ├── Tool Registry
              │     ├── 学习历史与计划
              │     ├── 查词与生词本
              │     ├── 内容生成
              │     └── 页面跳转
              └── PostgreSQL
```

第二阶段继续采用模块化单体，不引入微服务、Redis、消息队列或多 Agent 框架。普通对话和短内容生成由 API 进程完成；PDF、OCR、长音频等耗时任务留到第三阶段再增加独立 worker。

## 3. Provider 适配层

业务代码只依赖统一的 `LLMProvider` 契约，不直接依赖厂商响应结构：

```text
chat(messages, tools, model) -> normalized response
stream(messages, tools, model) -> normalized events
test_connection(model) -> latency and resolved model
```

每个 Provider 声明自己的：

- 官方 API 地址；
- 默认模型和可选模型；
- 流式、Tool Calls、图片、文件、推理模式等能力；
- 请求参数差异；
- 错误码映射。

模型名称保持可配置，避免厂商更新模型后修改业务代码。第一批实现 DeepSeek 和 MiniMax 的 OpenAI 兼容文本接口，后续可在适配器内部切换协议而不影响 Agent 工具。

## 4. API Key 安全

用户 API Key 只提交到 FastAPI：

1. 后端使用 `AI_CREDENTIAL_ENCRYPTION_KEY` 加密；
2. 数据库保存密文和末四位，不保存明文；
3. 浏览器重新加载后只得到掩码；
4. 调用厂商前在内存中短暂解密；
5. 日志、异常、审计记录不得包含 Key；
6. 加密主密钥仅存在于服务器 `.env` 和离线备份中。

如果加密主密钥丢失，已保存的厂商 Key 无法恢复，只能由用户重新输入。生产备份必须同时覆盖数据库和加密主密钥，但二者应分开保存。

第一版只允许使用代码内置的厂商官方地址，不接受任意 `base_url`，避免服务器端请求伪造。

## 5. Agent 执行循环

一次请求最多执行有限轮工具调用：

1. 保存用户消息；
2. 构建最近对话、对话摘要和必要用户偏好；
3. 将当前允许的工具定义发送给模型；
4. 校验模型返回的工具名和 Pydantic 参数；
5. 根据风险等级自动执行或等待确认；
6. 保存工具执行记录；
7. 将工具结果返回模型生成最终回答；
8. 通过 SSE 返回文本、卡片、确认请求和页面跳转事件。

建议限制：单轮最多 6 次模型往返、10 次工具调用、60 秒普通请求超时。写操作顺序执行；互不依赖的只读工具后续可以并行。

## 6. 工具风险等级

| 等级 | 示例 | 策略 |
|---|---|---|
| 只读 | 查词、历史、复习计划、学习统计 | 自动执行 |
| 导航 | 打开学习页、文章页、生词本 | 仅允许站内枚举路由，自动执行 |
| 可撤销写入 | 新建生词本、添加单词、修改备注 | 明确意图下自动执行并提供撤销 |
| 破坏性写入 | 删除生词本、批量移除单词 | 必须二次确认 |
| 高成本生成 | 长文章、批量语音、OCR | 展示范围或成本后确认 |

Agent 不提供任意 SQL、任意 HTTP 请求、任意文件系统访问或通用代码执行工具。

## 7. 学习事实与记忆

### 7.1 学习事实

学习记录、生词、收藏和复习时间由领域工具实时查询数据库。不能依赖模型“记住”这些信息，也不能把全部历史记录复制进每次提示词。

### 7.2 对话历史

`ai_conversations` 和 `ai_messages` 保存完整对话。短期上下文使用最近消息；旧消息压缩为可更新摘要，以控制 Token 成本。

主页历史列表默认收起。用户引用旧对话时，Agent 通过受限工具在当前用户全部会话中做有界关键词检索；不会把所有历史原样提交给模型厂商。

### 7.3 长期偏好

只保存稳定且对学习有帮助的偏好，例如学习目标、喜欢的文章主题和回答风格。临时聊天内容不能自动升级为长期记忆。

### 7.4 每日计划快照

现有 `study_reviews` 可以回答“实际复习了什么”，但复习完成后 `next_review_at` 会变化，无法还原“当天原计划是什么”。因此后续增加：

- `daily_study_plans`：用户、日期、时区、算法版本、计划统计；
- `daily_study_plan_items`：计划中的单词、学习类型和完成状态。

明日计划属于预测值，必须向用户说明它可能随今天的学习结果变化。

## 8. 自定义生词本重构

保留 `vocabulary_items` 作为“用户拥有这个生词”的事实，再增加：

- `vocabulary_collections`：用户创建的生词本；
- `vocabulary_collection_items`：生词与生词本的多对多关系。

同一个单词可以出现在多个生词本中。删除某个生词本只删除分类关系，不删除单词学习进度；“从所有生词中彻底移除”使用独立操作。

## 9. 前端事件协议

对话接口采用 POST + SSE 流式返回，主要事件包括：

- `message.delta`：文本增量；
- `message.completed`：回答完成；
- `tool.started`：工具开始；
- `tool.completed`：工具成功及结构化卡片；
- `tool.failed`：工具失败；
- `confirmation.required`：等待用户确认；
- `navigation.requested`：请求前端跳转到允许的站内页面；
- `usage.completed`：Token、耗时和厂商信息。

页面跳转使用 `page=learn|articles|vocabulary|wordbooks|profile` 等枚举，由前端映射成真实路由，模型不能返回任意 URL。

- 对话在刷新和重新登录后仍可恢复；
- Agent 对今天、昨天和明天的回答来自数据库工具且可测试；
- “开始学习”可以跳转到学习页；

- API Key 不出现在接口响应、日志、Git 或前端存储中；
- 后端测试、前端 lint/build 和数据库迁移全部通过。
