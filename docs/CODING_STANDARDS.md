# 编码规范

最后核对：2026-09-07。本规范描述当前技术栈的共同约定；具体行为仍以代码、测试和迁移为准。

## 1. 通用原则

- 优先小而完整的变更：实现、测试、文档和迁移一起交付。
- 延续现有模块化单体，不为局部需求引入微服务、消息队列或新框架。
- 公共契约显式建模，避免依赖隐式字典结构、字符串约定或前端猜测。
- 对用户数据、安全、金钱/额度、删除和外部调用采用更严格的验证与审计。
- 注释解释“为什么”和边界条件，不复述代码；复杂决策写入 `DECISIONS.md`。
- 不顺手格式化或重写无关文件，不掩盖用户已有改动。

## 2. Python / FastAPI

### 2.1 版本与格式

- 目标 Python 3.13；代码至少保持与 `pyproject.toml` 的 Python 3.12 语法目标兼容，除非同时调整该配置。
- 使用类型注解、现代联合类型 `A | None` 和清晰的返回类型。
- 行宽目标 100 字符，与 Ruff 配置一致。当前依赖中没有固定 Ruff 版本，不把未安装的 Ruff 当作 CI 门禁。
- 导入顺序保持标准库、第三方、项目模块三组；删除无用导入。
- 非显然算法、协议或安全边界使用短 docstring。

### 2.2 分层

```text
api/routes     HTTP、Depends、状态码和序列化边界
schemas        Pydantic 请求/响应契约
services       可测试的领域规则和外部 Provider 编排
models         SQLAlchemy 映射与数据库约束
db             Engine、Session、迁移和种子入口
core           配置、认证和共享基础设施
```

- 路由函数负责鉴权、解析输入、调用领域服务和映射 HTTP 错误；复杂查询/写入移入服务层。
- 请求和响应使用 Pydantic 模型。不要把 SQLAlchemy 对象、密文或内部异常直接返回给浏览器。
- 共享领域逻辑不能复制到多个路由；抽取成服务函数并直接测试。

### 2.3 用户隔离

用户私有资源的读取、更新和删除都必须在数据库条件中带入当前用户：

```python
select(Resource).where(Resource.id == resource_id, Resource.user_id == current_user.id)
```

不能先只按 `id` 读取再依赖调用方判断。关联表查询也要能通过父资源证明归属。新增用户域功能至少测试：自己的资源成功、他人的资源不可见/不可改、重复请求行为确定。

### 2.4 事务和幂等

- 一个业务操作形成清晰事务；成功后提交，异常时让 Session 回滚或显式回滚后再复用。
- 服务函数是否提交必须保持一致且从名称/调用点可判断。大型重构前先记录当前事务边界。
- 创建集合、关联、工具调用等可能重试的操作使用唯一约束和幂等策略。
- 外部网络调用不要夹在不可控的长数据库事务中。
- 破坏性 Agent 操作保存经校验的原始参数，确认后执行同一份参数，不能再次让模型改写目标。

### 2.5 时间

- 当前数据库 `DateTime` 使用 naive UTC，统一通过 `utc_now()` 或等价 UTC 转换生成。
- 用户自然日期由 `User.timezone` 的 IANA 名称换算，不能按服务器本地日期推断。
- 新接口返回时间时使用 ISO 8601；若改变时区/aware datetime 策略，必须设计迁移和兼容测试。

### 2.6 校验与错误

- 长度、枚举、范围和格式优先在 Pydantic schema 声明。
- 领域冲突使用稳定的领域异常，在路由层映射为合适的 4xx；未知异常不向客户端泄露堆栈和凭证。
- 404/403 的选择要兼顾资源枚举风险；当前用户看不到的私有资源优先按“不存在”处理。
- 不用 `except Exception: pass`。允许降级时记录安全化上下文并返回明确状态。

### 2.7 数据库迁移

- 修改 `entities.py` 必须新增 `apps/api/alembic/versions/NNNN_description.py`。
- 不修改已发布的 `0001`、`0002`、`0003`。
- 升级脚本考虑 SQLite batch 模式和 PostgreSQL 实际行为。
- 新增非空字段要提供服务端默认值或分阶段回填；删除/改类型前说明数据保留和回滚方案。
- 先在空库升级，再在带旧数据的副本上升级；生产前备份。

### 2.8 Agent 与 Provider

- 业务层只依赖统一 Provider 契约，不在路由里解析厂商专属响应。
- Provider 地址来自服务端白名单，不允许用户传任意 `base_url`。
- Tool 名称和参数必须注册并通过 Pydantic 校验；工具实现只获得完成任务所需的最小能力。
- 学习事实实时查数据库，不能依赖模型记忆。
- 每轮步骤、工具数、输出 Token、超时和重试必须有上限。
- 增加工具时定义风险等级、幂等规则、确认规则、审计结果和前端卡片行为。

## 3. TypeScript / Next.js

### 3.1 结构与类型

- 使用 App Router；页面位于 `apps/web/app`，复用组件位于 `apps/web/components`。
- 共享 API 类型集中在 `apps/web/lib/types.ts`，请求集中在 `apps/web/lib/api.ts`。
- 保持严格 TypeScript，不用 `any` 逃避协议建模；第三方不可信数据先以 `unknown` 接收并收窄。
- 只有需要浏览器 API、状态或事件时才使用 Client Component；避免无必要扩大客户端边界。
- 不在页面中拼接 API 根地址或复制 Token 读写逻辑。

### 3.2 状态与请求

- 每个异步界面明确处理：初始加载、空数据、成功、可恢复错误、401 和请求取消。
- 写操作防止重复点击；乐观更新必须有失败恢复。
- SSE 消费保持事件类型显式，未知事件应安全忽略或记录，不能让单个坏事件破坏整个会话。
- 刷新后的会话/工具卡片以服务器持久化数据恢复，不能只依赖组件内存。

### 3.3 UI 与可访问性

- 所有主要流程同时支持约 360px 移动宽度和常见桌面宽度。
- 使用语义化元素；图标按钮有可访问名称，表单控件有标签，键盘焦点清晰。
- 颜色不是唯一状态提示；错误、成功和确认使用文字反馈。
- 遵循现有字体、颜色和布局语言。大范围视觉重设计需要单独任务和验收。
- 梧桐形象当前不在 UI 开发范围。

### 3.4 环境变量

- 浏览器只读取 `NEXT_PUBLIC_*`；这些值会进入构建产物，按公开信息处理。
- 本地默认 API 路径为 `/api/v1`，开发时由 Next.js rewrite 到 `localhost:8000`。
- 修改构建参数时同步检查 Dockerfile、Compose、`.env.example` 和部署文档。

## 4. API 契约

- 公共前缀保持 `/api/v1`。不兼容变化优先新增字段或新版本，不静默改变既有字段含义。
- 成功和错误状态码符合 HTTP 语义；删除成功当前使用 204。
- 客户端可见错误保持简洁、稳定、可操作，不包含内部类名、SQL 或厂商密钥。
- 列表变大前引入统一分页，不能让不同端点各自发明格式。
- SSE 事件名和数据结构属于跨端契约，修改时同步前后端、测试和 `API.md`。

## 5. 数据、词库与内容

- `Word` 是全局共享词典；`UserWordProgress`、`VocabularyItem` 等保存用户状态。
- 词书顺序通过 `WordbookWord.position` 表达，导入和更新不得随意打乱已发布顺序。
- 外部词库进入数据库前执行格式、长度、重复、字符、来源和授权校验，详见 `WORDLIST_PIPELINE.md`。
- 不用 AI 在导入时无标记地补造音标、释义或例句。生成内容必须有 `source_type`/元数据并与来源数据区分。
- 种子数据用于开发演示，不承载批量生产词库。

## 6. 依赖与日志

- Python 依赖固定在 `requirements.txt`；前端使用 `package-lock.json` 和 `npm ci`。
- 升级框架或加依赖时运行完整测试/构建，记录破坏性变化和许可证影响。
- 日志包含操作类型、请求/会话标识、耗时和安全化错误；不包含密码、Token、完整 API Key、Authorization header 或用户上传正文。
- Provider 错误在保留排障价值的同时屏蔽凭证和不必要的厂商响应正文。

## 7. 代码评审检查

- 是否在正确层实现，是否复制了已有逻辑？
- 是否保持用户隔离、事务和幂等？
- 是否改变 API、SSE、表结构、环境变量或部署？
- 是否覆盖成功、失败、越权和重复请求？
- 是否影响移动端、可访问性或加载/空/错误状态？
- 是否引入凭证、数据授权或供应链风险？
- 是否更新对应文档并给出实际验证结果？
